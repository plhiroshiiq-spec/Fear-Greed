対象: SPEC.md 9.2章。

> 寄り前の外部環境を1つだけ。既定はSOX指数の前日比%。データ源は無料のものをP5で選定し、
> 取得失敗時は枠ごと非表示にする(誤った値は絶対に出さない)。

- **結論: engine(GitHub Actions)が取得し、`data/ext.json` に前日比%だけを置く。** ← 方針は有効
- **⚠️ ソースは未確定。stooq / Yahoo はどちらも GitHub Actions から使えないことが実測で判明した(3章)。**
- 判断日: 2026-09-18 / 運用費: **0円**

---

## 1. なぜアプリから直接叩かないか

SUMI DECK から直接ソースを叩くと、次が全部アプリ側の問題になる。

- ソースの仕様変更・遮断でアプリが壊れる(更新にストア配信が要る)
- 端末ごとに取得が走り、ソースに余計な負荷をかける
- 検証ロジックを Kotlin にもう1本持つことになる

engine 側に寄せれば、**アプリは既に読んでいる raw URL をもう1本読むだけ**で済む。
ソースが変わっても engine の更新だけで直る。fg.json と同じ経路なので、
キャッシュ・stale の扱いも使い回せる。

## 2. 保存するもの

**前日比%だけ。** 指数の水準そのものは保存しない。SPEC.md 8章の「保存するのはスコアと
派生統計のみ」と同じ方針で、再配布の問題を避ける。`tools/check_no_raw_data.py` が
`ext.json` のキーを機械的に検査する。

```json
{
  "schema": 1,
  "generated_at": "2026-09-18T06:41:12+09:00",
  "ext": {
    "key": "sox", "name_ja": "SOX指数", "source": "stooq",
    "as_of": "2026-09-17", "change_pct": -1.50, "stale": false
  }
}
```

## 3. ソースの選定

| ソース | URL | 費用 | APIキー | 位置づけ |
|---|---|---|---|---|
| stooq | `https://stooq.com/q/d/l/?s=^sox&i=d` | 無料 | 不要 | 第1候補。CSVで形が単純 |
| Yahoo Finance | `https://query1.finance.yahoo.com/v8/finance/chart/^SOX` | 無料 | 不要 | 予備。非公式で遮断されることがある |

### 実測の結果(2026-09-18 08:57 UTC / `fg` run #2)— **両方とも失敗**

| ソース | HTTP | 実際に返ってきたもの |
|---|---|---|
| stooq | **200** | CSVではなく **JavaScript のボット判定ページ**。`this site requires javascript to verify your browser` |
| Yahoo Finance | **429** | Too Many Requests |

どちらも**データセンターのIPからの取得を弾いている**。GitHub Actions のランナーは
データセンターIPなので、ブラウザ風の `User-Agent` を付けても(実際に付けている)通らない。
Yahoo の 429 は瞬間的なレート超過ではなく、クラウドIPに対する恒常的な制限と見るのが自然。

**この2本は再試行しても通らない。** 別のソース、または別の指標に切り替える必要がある
(選択肢は6章)。

**設計としては想定どおりに壊れた**: `ext.json` は作られず、`fg.json` の更新(同じ実行で
CNN から score 28.71 を取得済み)には一切影響していない。終了コードも0。

### 当初この2本を選んだ経緯

P5 の作業環境は外向き通信がポリシーで制限されており、どちらのホストにも到達できなかった
(P4 と同じ制約。docs/price_source.md 参照)。GitHub Actions のランナーからは外に出られる
ことが P1 で実証済み(CNN の取得に成功している)だったため、**初回のワークフロー実行を
実地の検証にあてた**。その検証で不合格になった、というのが上の結果である。

- ソースは順に試し、片方が落ちてももう片方で拾う
- 検証(下記)に1つでも外れたら**採用しない**
- すべて失敗しても**既存の ext.json を上書きせず**、`stale:true` だけ立てる
- **終了コードは常に0**。EXT は任意機能なので `fg.json` の更新を巻き込まない

なお SOX は**指数**なので、P4 で問題にした株式分割の調整は関係しない。
指数の構成銘柄入れ替えは指数値の計算側で吸収される。

## 4. 妥当性検証(1つでも外れたら採用しない)

| 条件 | 理由 |
|---|---|
| `as_of` が未来でない | 時刻ずれや形式取り違えの検出 |
| `as_of` が7日以内 | 連休を考慮しつつ、止まったソースを弾く |
| `|change_pct| <= 30` | 指数で1日30%は起きない。桁の取り違えを弾く |
| 2行以上の終値が取れている | 前日比が計算できない状態で数値を作らない |

## 5. 表示側の扱い

9.2章は「取得失敗時は枠ごと非表示」としているが、6.1章・6.4章は「完全非表示は手動オフの時だけ」
「取得失敗で枠を消すことを禁止」としており、**両者が正面から衝突する**。
経緯と現在の実装は `docs/spec_diff.md` D16 に記録した。**発注者の判断待ち**。

どちらを選んでも「誤った値は絶対に出さない」(9.2章)は守る。`stale` の EXT の数値は出さない。

## 6. 次の選択肢(**発注者の判断待ち**)

stooq / Yahoo が使えない以上、次のどれかを選ぶ必要がある。

### (A) EXT を見送る(何もしない)

SPEC.md 9.2章は EXT を**任意**としている。可変枠は SL WATCH(9.1章・本命)で埋まるので、
EXT が無くても運用に穴は開かない。実装は残っているので、使えるソースが見つかった日に
`fg/ext.py` へ1関数足すだけで動く。**いちばん安い選択肢。**

### (B) 指標を S&P500 の前日比%に変える

**CNN の同じペイロードに S&P500 の日足が入っている**(`market_momentum_sp500.data`)。
すでに毎日取得に成功しているので、**新しい通信を1本も増やさずに** EXT を動かせる。
確実に動くことが実証済みで、APIキーも契約も不要。

欠点: SOX(半導体)ほど尖っていない。寄り前に見て意味があるかは発注者の判断。
その場合 `key` は `sp500`、`name_ja` は `S&P500` にして、**SOXだと誤解させない**。

### (C) 別の無料ソースを探す

APIキー不要でクラウドIPから叩けるものを探す。候補は限られ、見つかっても
「いつ弾かれるか分からない」性質は同じ。**調べる手間の割に不確実。**

### (D) APIキーが要る無料枠を使う

Alpha Vantage / Twelve Data / Finnhub などに無料枠がある。**課金は発生しない**が、
SPEC.md 10章の「APIキーの取得も課金も不要」に反する。登録とシークレット管理が増える。
**発注者が明示的に望まない限り実装しない。**

---

**現時点の推奨は (A) か (B)。** EXT は任意機能なので、手間をかけずに済ませるなら (A)、
枠に何か出したいなら (B) が確実に動く。

## 7. 別の指標に変える場合の作業

`fg/ext.py` の `KEY` / `NAME_JA` と、各ソース関数のシンボル(`^sox`)を変えるだけでよい。
検証のしきい値は指数を前提にしているので、個別株や為替に変える場合は見直すこと。
