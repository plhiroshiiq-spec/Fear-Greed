# 丸め規則の判定記録

対象: SPEC.md 1.3章「値の精度」。CNNは `score` を小数のfloatで配信する
(例 `29.6285714…`)。SUMI DECK は整数で表示するため、**四捨五入か切り捨てか**を
確定させる必要がある。1ポイントの差が区分の境界(25 / 45 / 55 / 75)をまたぐ日があるため、
どちらでもよい話ではない。

- 判定結果: **未確定(暫定 = 四捨五入)**
- 暫定値の根拠: SPEC.md 1.3章「確定するまでは四捨五入とし、判明後に統一する」
- 規則の定義箇所: `fg/rounding.py` の `DISPLAY_RULE`(engine 側の唯一の定義箇所)
- 最終更新: 2026-09-18

---

## 1. なぜ P1 で確定できなかったか

P1 の開発環境(Claude Code のリモート実行コンテナ)は外向き通信がポリシーで制限されており、
CNN の2ホストがどちらも遮断されていた。

| ホスト | 結果 |
|---|---|
| `production.dataviz.cnn.io:443` | egress proxy が CONNECT に 403(ポリシー拒否) |
| `www.cnn.com:443` | 同上 |

つまり **JSON も表示値もこの環境からは1日ぶんも取得できない**。実測なしに
「四捨五入だった」と書くことは設計原則1(壊れても嘘をつかない)に反するため、
確定させずに観測の仕組みだけを用意した。

GitHub Actions のランナーからは両ホストに到達できるため、**観測は稼働後に自動で貯まる**。

## 2. 判定方法

`floor`(切り捨て)と `round_half_up`(四捨五入)は、小数部が 0.5 以上の日にしか
違いが出ない。29.63 なら 29 と 30 に割れるが、29.30 はどちらも 29 になる。
したがって **小数部 0.5 以上の営業日(= 判別可能日)を3日**そろえる。

手順:

1. 毎日の `fg` ワークフローが `python -m fg.rounding_probe --observe` を実行し、
   `data/rounding_probe.csv` に1行追記する。記録するのは `score`(小数)と
   両方の候補値、そして判別可能かどうか。
2. 発注者が https://www.cnn.com/markets/fear-and-greed を開き、**画面に出ている整数**を
   同じ行の `site_display` 列に書き込む(1日あたり5秒)。
   このとき **CNNの画面上の "Last updated" が CSV の `as_of` と同じ日**であることを必ず確認する。
   別の時点の値と突き合わせると判定が壊れる。
3. 判別可能日が3日そろったら `python -m fg.rounding_probe --decide` を実行する。
4. 出力された規則を `fg/rounding.py` の `DISPLAY_RULE` に書き、本ファイルの
   「判定結果」を更新する。P2(Kotlin)側も同じ規則で実装する。

CNN のページはスコアを JavaScript で描画するため、表示値は HTTP 取得では読めない。
自動化するにはヘッドレスブラウザが要るが、DOM セレクタに依存して静かに壊れる仕組みを
1回だけの判定のために入れるのは割に合わないと判断し、その1列だけ手入力にしている。

## 3. 観測記録

`data/rounding_probe.csv` が一次記録。ここには要約だけを残す。

| as_of | score(CNN JSON) | 切り捨て | 四捨五入 | CNN画面の表示 | 判別可能 | 出典 |
|---|---|---|---|---|---|---|
| 2026-09-17 | 29.6285714… | 29 | 30 | 29 | yes | SPEC.md 1.3章(発注者の観測) |
| — | — | — | — | — | — | (ワークフロー稼働後に追記) |
| — | — | — | — | — | — | (ワークフロー稼働後に追記) |

**現時点の示唆**: 1日ぶんの観測は「切り捨て」を支持している(四捨五入なら 30 と出るはず)。
ただし1日では、CNN の画面が JSON と違う時点の値を表示していた可能性(ザラ場中の更新ずれ)を
排除できない。SPEC.md が3営業日ぶんを求めているのはそのためであり、この1点だけで
`DISPLAY_RULE` を変えることはしない。

## 4. 判定が矛盾した場合

`--decide` が `conflicts` を返す(どちらの規則でも説明できない日がある)場合は、
丸め以外の原因を疑う。具体的には次の順で確認する。

1. `site_display` を読んだ時刻と `as_of` がずれていないか(最も多い原因)
2. CNN が表示側だけ別の系列(例: 直近の確定値ではなく暫定値)を使っていないか
3. 小数第1位ではなく別の桁で丸めていないか(例: 0.5刻み)

矛盾を無理に片付けず、CSV の該当行を残したまま本ファイルに経緯を書くこと。

## 5. 既知の限界

`data/fg.json` の `us.score` は SPEC.md 2章の例に合わせて**小数第2位**で保存している
(例 `29.63`)。真の値が整数の 0.005 以内にある日(例 `29.9987`)は、2桁に丸めた時点で
`30.00` になり、切り捨て規則でも 30 と表示されてしまう。発生確率は1営業日あたり約1%で、
ずれても1ポイントだが、**切り捨てに確定した場合はこの点を P2 の判断材料にすること**。
回避するなら `fg.json` に整数の表示値(`score_display`)を追加して engine 側で確定させる。
schema 2 の契約を変える話なので、P1 では入れていない。
