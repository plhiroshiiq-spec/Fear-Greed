# 丸め規則の判定記録

対象: SPEC.md 1.3章「値の精度」。CNNは `score` を小数のfloatで配信する
(例 `28.5428571…`)。SUMI DECK は整数で表示するため、**四捨五入か切り捨てか**を
確定させる必要がある。1ポイントの差が区分の境界(25 / 45 / 55 / 75)をまたぐ日があるため、
どちらでもよい話ではない。

- **判定結果: 切り捨て(`floor`)**
- 判定日: 2026-09-18
- 規則の定義箇所: `fg/rounding.py` の `DISPLAY_RULE`(engine 側の唯一の定義箇所)
- 一次記録: `data/rounding_probe.csv`
- SUMI DECK(Kotlin)側も**同じく切り捨て**で実装すること。`Math.round()` を使わない。

---

## 1. 判定の根拠

2026-09-18 13:20 JST の `fg` run #1 が取得した値と、同日に発注者が CNN の画面で読み取った
整数を突き合わせた。

| 画面のラベル | CNN JSON の値 | 画面の表示 | 切り捨てなら | 四捨五入なら | 判定 |
|---|---|---|---|---|---|
| Previous close | 28.69 | **28** | 28 ✅ | 29 ❌ | 切り捨て |
| 1 week ago | 32.69 | **32** | 32 ✅ | 33 ❌ | 切り捨て |
| 1 month ago | 54.63 | **54** | 54 ✅ | 55 ❌ | 切り捨て |
| 1 year ago | 66.54 | **66** | 66 ✅ | 67 ❌ | 切り捨て |

4つとも小数部が 0.5 以上(.69 / .69 / .63 / .54)なので**両規則が別の整数になる**。
その4つすべてが切り捨てと一致し、四捨五入とは1ずつずれた。区分名
(Fear / Fear / Neutral / Greed)も4つとも一致しており、同じ値を見ていることが裏付けられる。

SPEC.md 1.3章に記録されていた観測(2026-09-17: `29.6285714…` → 画面 `29`)も切り捨てと
一致する。四捨五入なら 30 と出るはずだった。**合計5件、矛盾は0件。**

## 2. なぜこの4値で判定したか(現在値を使わなかった理由)

CNN の画面は5つの数値を出すが、**比較に使えるのは確定済みの4値だけ**である。

| 値 | 比較に使えるか | 理由 |
|---|---|---|
| メインゲージ(現在値) | **使えない** | 刻々と動く。API取得の時刻と画面を読んだ時刻が数分ずれるだけで別の値になり、丸めのせいなのか時点差のせいなのか区別できない |
| Previous close / 1週 / 1か月 / 1年 | 使える | すでに確定した過去の値であり、その日のうちは動かない。取得と読み取りに時間差があっても同じ値を指す |

実際、今回のメインゲージは画面が `29`、API取得値が `28.5428571…` で、切り捨てなら 28 に
なるはずだった。これは**丸めの矛盾ではなく時点差**である。両者は同じ営業日の値だが、
API を叩いた 13:20 JST と発注者が画面を見た時刻の間に現在値が動いている。確定済みの4値が
完全に一致していることが、同じ配信を見ている証拠になっている。

`fg/rounding_probe.py` はこの区別を `comparable` 列として持ち、現在値の行を記録はするが
判定からは除外する。

**SPEC.md は「3営業日ぶん照合」を求めていたが、確定済み4値はそれぞれ別の営業日
(前営業日・1週前・1か月前・1年前)を指すため、1回の取得で4営業日ぶんの照合になっている。**
しかも全て同一時点の読み取りなので、3日に分けるより時点ずれの危険が小さい。
この読み替えは `docs/spec_diff.md` D9 に記録した。

## 3. 再確認の手順

CNN が表示の実装を変えた疑いが出たときは、同じ手順で確認できる。

1. `python -m fg.rounding_probe --observe` で `data/rounding_probe.csv` に5行追記する
   (毎日の `fg` ワークフローが自動で実行している)。
2. https://www.cnn.com/markets/fear-and-greed を開き、`comparable=yes` の4行の
   `site_display` 列に画面の整数を書き込む。
3. `python -m fg.rounding_probe --decide` を実行する。
4. 結果が変わっていたら `fg/rounding.py` の `DISPLAY_RULE` と本ファイルを更新し、
   SUMI DECK 側も合わせる。

## 4. 判定が矛盾した場合

`--decide` が `conflicts` を返す(どちらの規則でも説明できない観測がある)場合は、
丸め以外の原因を疑う。順に確認する。

1. 画面を読んだ時点と CSV の `as_of` がずれていないか(最も多い原因)
2. `comparable=no` の行(現在値)を誤って判定に混ぜていないか
3. CNN が小数第1位ではなく別の桁で丸めていないか(例: 0.5刻み)

矛盾を無理に片付けず、CSV の該当行を残したまま本ファイルに経緯を書くこと。

## 5. 既知の限界

`data/fg.json` の `us.score` は SPEC.md 2章の例に合わせて**小数第2位**で保存している
(例 `28.54`)。真の値が整数の 0.005 以内にある日(例 `29.9987`)は、2桁に丸めた時点で
`30.00` になり、**切り捨て規則でも 30 と表示されてしまう**。発生確率は1営業日あたり約1%で、
ずれても1ポイント。

切り捨てに確定した以上この穴は残るので、P2 で次のどちらかを選ぶこと。

- (a) 許容する。1%の日に1ポイントずれるが、区分の境界に当たる確率はさらに低い。
- (b) `fg.json` に整数の表示値(`score_display`)を追加し、engine 側で全精度から確定させる。
  schema 2 の契約が変わるため、SUMI DECK 側の実装前に決める必要がある。
