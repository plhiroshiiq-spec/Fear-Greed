## D1. 開発環境から CNN に到達できない(環境の制約。仕様の誤りではない)

Claude Code のリモート実行コンテナは外向き通信がポリシーで制限されており、
`production.dataviz.cnn.io:443` と `www.cnn.com:443` がどちらも egress proxy で
403(CONNECT 拒否)になる。

影響:

- CNN の実ペイロードでの動作確認が P1 ではできていない。テストは SPEC.md 1.2章の
  構造を写した**合成データ**(`tests/synthetic.py`)で行っている。
- 丸め規則を3営業日ぶん照合できていない。詳細と代替手順は `docs/rounding.md`。

対処: GitHub Actions のランナーは両ホストに到達できるため、実データでの検証は
初回のワークフロー実行で行う。1.2章の構造(キー名・`x` が ms、`y` がスコア)が
実物と違っていた場合は `fg/cnn.py` の `validate()` が弾き、既存の `fg.json` は壊れない。

**課金が必要な外部サービスは不要**。有料のプロキシや株価APIを足せば回避できるが、
0円方針(設計原則4)を破ってまで解決する問題ではないと判断した。

## D2. SPEC.md 2章の例で `delta` と `prev_close` が整合しない

例では `score: 29.63` / `prev_close: 26.49` / `delta: -2.34` となっているが、
`29.63 − 26.49 = +3.14` であり、定義「`delta` = 当日 − 前日」と合わない。
例示用の値が混ざったものと判断した。

実装: 定義のほうを採用し、`delta = score − prev_close`(CNN の `previous_close`)で計算する。
`streak` は `history` の日次差分から求める。`streak` の符号は `delta` の符号と一致する。

## D3. 要素スコアの精度

SPEC.md 2章の例が `26.4` / `3.0` / `0.2` のように小数第1位なので、`components[].score` は
小数第1位に丸めている。総合スコア `us.score` は丸めずに CNN の値をそのまま
(小数第2位で)運ぶ。1.3章の「7要素の単純平均」を `components` から再現しようとすると
丸め誤差で一致しないが、**総合値は自前で再計算しない**のが1.3章の指示なので問題にならない。

## D4. `components[].raw` のモメンタムだけが派生統計

`market_momentum_sp500.data[].y` は S&P500 の終値そのものだが、SPEC.md 2章の例は
`raw: 3.61`(= 1.4章の「125日線を +3.6% 上回っている」)になっている。
そこでモメンタムの `raw` だけ `(SP500 ÷ SP125 − 1) × 100` で算出している。
他の6要素は `data` の最終値をそのまま入れる。

## D5. 失敗時に `generated_at` を更新しない

SPEC.md 4章 手順3 は「既存の fg.json を上書きせず `stale:true` だけを立てる」とあるが、
`generated_at` を触るかどうかは書かれていない。

実装: **更新しない**。SUMI DECK 側は「`generated_at` が36時間以上前 or `stale:true` なら
更新遅延を表示」する(5章)ので、失敗のたびに `generated_at` を新しくすると
データが古いのに新鮮に見えてしまう。

## D6. 3回連続失敗のカウンタの置き場所

SPEC.md 4章 手順4 の「3回連続で失敗した場合」を数えるための状態が必要だが、
`fg.json` は schema 2 の契約なのでキーを足さない。`data/failure_state.json` を
別ファイルとして持つ。SUMI DECK はこのファイルを読まない。

## D7. Python のバージョン

SPEC.md 3章は Python 3.12 を指定している。CI(GitHub Actions)は 3.12 で動かす。
開発コンテナには 3.11 しか無かったため、3.11 でも動く書き方に留めている
(3.12 固有の構文は使っていない)。

## D8. `previous_close` と `history` の前営業日の値が一致しない(要観察)

初回の実データで次のずれが出た。

| 項目 | 値 |
|---|---|
| `fear_and_greed.score`(当日) | 28.54 |
| `fear_and_greed.previous_close` | 28.69 |
| `history` の 2026-09-17(前営業日) | 28.54 |
| `history` の 2026-09-18(当日) | 28.54 |

`delta` は定義どおり `score − prev_close = −0.15` になるが、`history` の日次差分は
`28.54 − 28.54 = 0.00` なので、`streak` が 0 になった。**`delta` が負なのに `streak` が 0**
という、見た目に矛盾する組み合わせが出る。

**原因の見立て**: この実行は 04:20 UTC(米東部 00:20)の**寄り前**に行った。米国の
09-18 のセッションはまだ始まっておらず、CNN は当日の行に前日の値をそのまま持ち越している。
一方 `previous_close` は別のタイミングで確定した値らしく、0.15 ずれた。
履歴250ペア中、隣接が同値なのは2ペアだけなので、**常時起きる現象ではない**。

**対処**: 実装は変えない。4章の定時実行(morning = 21:40 UTC = 米国引け後)では
当日の値が確定しているはずで、このずれは出ないと見ている。**翌営業日の morning 実行で
`prev_close` と `history[-2]` が一致するかを確認する**。定時実行でも一致しないなら、
`delta` の算出元を `history` の日次差分に切り替えるか検討する(`streak` と定義がそろう)。

SPEC.md 6.2章(`streak` の絶対値 ≥ 3 で展開)と 6.3章(連続日数は必須表示)が `streak` に
依存しているため、放置はできない論点として記録しておく。

## D9. 丸め規則の照合を「3営業日 × 1値」ではなく「1時点 × 4値」で行った

SPEC.md 3章 P1 は「3営業日ぶん、CNNサイトの表示値と `score` の小数を突き合わせ」と
指示している。実際には **1回の取得で、CNN画面が同時に出す確定済みの4値**
(Previous close / 1 week ago / 1 month ago / 1 year ago)と突き合わせて確定させた。

**理由**: 指示の狙いは「1日だけだと、画面とJSONが別の時点の値を指していた可能性を
排除できない」という点にあると読んだ。確定済みの4値はその日のうち動かないので、
取得と読み取りに時間差があっても同じ値を指す。しかも4値はそれぞれ別の営業日
(前営業日・1週前・1か月前・1年前)なので、**営業日の本数としても3日を満たしている**。
3日に分けるより時点ずれの危険が小さく、結論も早く出る。

現在値(メインゲージ)は刻々と動くため判定に使っていない。`fg/rounding_probe.py` は
この区別を `comparable` 列として持つ。詳細は docs/rounding.md 2章。

## D10. `history` の日次値と `previous_close` が同じ日でも一致しない(D8の続き)

D8 で記録した 0.15 のずれについて、CNN画面との照合で分かったことを追記する。

画面の「Previous close」は **28**(= `previous_close` 28.69 の切り捨て)であり、
`history` の前営業日 2026-09-17 の値 **28.54** ではなかった。つまり CNN 自身が
「前営業日の終値 = 28.69」と表示している。

したがって `history` の日次値は**その営業日の確定終値とは限らない**(配信の途中経過を
拾っている可能性がある)。`delta` は `previous_close` から計算しているので画面と整合するが、
`streak` は `history` の差分から求めているため、両者の定義がそろっていない。

**影響**: SPEC.md 5.1章の推移線(60営業日)と 6.2/6.3章の `streak` が `history` に依存する。
P2 に入る前に、定時実行(米国引け後)のデータで `history[-2]` と `previous_close` が
一致するかを確認すること。一致しないなら、`history` の最新1〜2本を確定値で置き換えるか、
`streak` の算出元を変えるかの判断が要る。

## D11. P2: SUMI DECK のコードベースを読めなかった / Android をビルドできなかった

SPEC.md 5章は「最初に既存コードベースを読み、DI・テーマ・画面構成・命名の流儀に
合わせること」と指示しているが、P2 の作業環境からは次の制約があった。

| 制約 | 内容 |
|---|---|
| SUMI DECK のリポジトリが見えない | このセッションから到達できるのは `Fear-Greed` のみ |
| Android SDK が無い | 開発コンテナに未インストール |
| Google Maven が遮断されている | `dl.google.com:443` が egress proxy で 403。Compose の依存を解決できない |

**対処**: 判断を伴う処理をすべて Android 非依存の `sumideck/core/` に寄せ、JVM のテスト
(53件)で検証した。Compose と取得の層(`sumideck/android/`)は「core が出した値を描く /
読む」だけにし、SUMI DECK に貼り込んでから初めてコンパイルされる前提にしてある。

**残っている作業**: SUMI DECK 側で実際にコンパイルし、既存の DI・テーマ・命名に合わせること。
手順は `sumideck/README.md` に書いた。**課金が必要な外部サービスは不要**(Android SDK は無料、
Google Maven も無料。遮断は環境側のポリシー)。

## D12. P2 検収の「履歴が18本未満」は v2.2 では60本が基準

SPEC.md 3章 P2 は「履歴が18本未満のときの挙動もテストすること」と書いているが、
v2.2 で推移線は 18営業日 → **60営業日**に変更されている(変更総括)。18 は v2.1 までの
本数なので、**60本未満の全域**が「足りない場合」に当たると読んだ。

テストは 0〜17本(元の指示の範囲)を1本ずつ確認したうえで、18本・60本・260本も確認している。
どの本数でも 0 や前値で埋めないことを検証した。
